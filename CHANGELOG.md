Programs that aren't in the repo are under [proofs/](proofs/) (one small Cargo project per check, pinned to the exact version or commit it runs against; its README has the command and what it printed).

Two uses in one module fail again with E0428, because the four helper fns it leaves at the call site have fixed names. And its static no longer equals the type's own vtable, which 0.3.1's own test asserted. A `waker_tables = "0.3"` requirement takes any 0.3.x on a plain `cargo update`, so this can't ship as a 0.3 patch.

### Fixed

**`derive_arc_unsafe_wakeable!`'s `wake_by_ref` could call a type's own functions.** 0.3.1 made the generated `wake_by_ref` call `Self::wake(Self::clone_ptr(ptr))`. A `Self::` path finds a type's inherent function before the trait's. So a type with its own safe `fn clone_ptr(p: *const Self) -> *const Self` had that one called in place of the trait's. The one in `tests/inherent_names.rs` takes no ref, so `wake` gives back a ref the waker still holds, and every `wake_by_ref` drops the count by one. That's a use-after-free from a program with no `unsafe`. And a wake method named `wake`, which 0.1.4 took, didn't compile, since `Self::wake` found it and handed it a `*const Self`. Now both calls name the trait: `<Self as $crate::UnsafeWakeable>::wake(<Self as $crate::UnsafeWakeable>::clone_ptr(ptr))`. 0.3.2 has the same fix.

### Added: what 0.1.4 had, back

Five things 0.1.4 could do that 0.2.0 or 0.3.0 took out. Where the 0.1.4 form let safe code cause Undefined Behavior, it comes back as an `unsafe fn`, and its `# Safety` says what the caller has to guarantee. The others come back safe, as they were. Safe code still can't reach that Undefined Behavior: the `compile_fail` doctests named below try the 0.1.4 attacks from safe code, and they don't build.

**A vtable chosen per waker.** 0.1.4 had `waker_from_arc(arc, &VTABLE)` and `raw_waker_from_ptr(ptr, &VTABLE)`, both safe, so one type could have wakers with different vtables. 0.2.0 dropped the vtable argument from both, because safe code could hand `waker_from_arc` an `Arc<A>` with `B`'s vtable and get a `Waker` that reads an `A` as a `B` (the first Security entry under 0.2.0). Now `unsafe fn waker_from_arc_with_vtable(arc, &VTABLE)` does what 0.1.4's `waker_from_arc` did. It's `unsafe` because it builds the `Waker` itself, so that's where a wrong vtable becomes a waker; its `# Safety` says what the vtable must do with the data pointer and the refcount. `fn raw_waker_from_ptr_with_vtable(ptr, &VTABLE)` is safe, as 0.1.4's `raw_waker_from_ptr` was: it only builds a `RawWaker`, which does nothing until the `unsafe` `Waker::from_raw`. `waker_from_arc(arc)` and `raw_waker_from_ptr(ptr)` are unchanged.

**`declare_raw_waker_vtable!` as in 0.1.4.** In 0.1.4 the declared static's clone fn returned a `RawWaker` on that same static, so a waker built on it kept it through every clone, and `will_wake` held between them. The cost is the one-per-module limit and the inequality under "Why 0.4.0".

**Task vtables built by hand, and read.** 0.1.4's `UnsafeWakeableVTable` was three `pub` fn fields, so you could write one as a struct literal around your own functions (logging, wrappers, shims) and read `poll_fn` back out. 0.2.0 added `pub` `type_id` and `type_name` so `RegisteredTask::new` could check the type. 0.3.0 made every field private, because a hand-written vtable could record one type with another type's functions and pass that check (the Security entry under 0.3.0). The fields stay private. `UnsafeWakeableVTable::from_raw_parts::<T>(poll_fn, wake_fn, drop_fn)` is a `const unsafe fn`, so it works in a `static`, and it records `T` as the vtable's type. It's `unsafe` for the reason the fields went private: `RegisteredTask::new` trusts the recorded type. `poll_fn()`, `wake_fn()` and `drop_fn()` hand the functions back and are safe, since calling one takes `unsafe`. `of::<T>()` now builds through `from_raw_parts`. With a hand-built vtable, the function that runs is the one passed in, not `T`'s trait function. So the `# Safety` of `poll`, `wake` and `drop_in_place` on `UnsafeWakeablePtr` and `RegisteredTask` now name the vtable's function. For a vtable from `of` or `derive_unsafe_wakeable_vtable!`, that is `T`'s `UnsafeWakeableTask` method. For one from `from_raw_parts`, it is the passed-in function's own contract. In 0.3.1 they said "the task's own" contract.

You could write `RegisteredTask { key, ptr }` over any memory, also in a `const`, and move `ptr` back out, and nothing was ever freed. 0.2.0 made the fields private, so `RegisteredTask` could free its box on drop and safe code couldn't swap a pointer under another type's vtable (the second Security entry under 0.2.0). Now `const unsafe fn RegisteredTask::from_raw_parts(key, ptr)` builds one that `RegisteredTask`'s `Drop` never frees, and `fn into_raw_parts(self) -> (VTableKey, UnsafeWakeablePtr)` hands the pointer back without freeing it. `from_raw_parts` is `unsafe` because `poll`, `wake` and `drop_in_place` trust the pointer and the vtable to match, and it records `key` without looking it up. Its `# Safety` asks for a pointer valid for reads and writes as the vtable's type for as long as the task exists, never derived from `&x`, since `poll` and `drop_in_place` write through it. `into_raw_parts` is safe and `#[must_use]`: throwing its result away leaks a task made by `new`. `new` and its type check are unchanged.

### Changed

**The data pointer rule, written once.** `RegisteredTask::from_raw_parts`, and `poll`, `wake` and `drop_in_place`, hand `ptr.data` to the vtable's functions, which read it as one type. "The data pointer" in `UnsafeWakeablePtr`'s docs now says what that memory may be: that type, a `#[repr(transparent)]` wrapper of it, or a `#[repr(C)]` struct whose first field is that type. It has to be valid for reads, and for `poll` and `drop_in_place` also writes, and hold a valid value. It also names what isn't enough: a type that only has the same size and alignment, a struct without `#[repr(C)]`, and for writes, a pointer derived from `&x`. The `# Safety` sections of `RegisteredTask::from_raw_parts`, `UnsafeWakeablePtr::poll` and `wake` (`drop_in_place` is as `poll`) and `UnsafeWakeableVTable::from_raw_parts` state it and link there. 0.3.1 asked for "a live task of the type `self.vtable` was built for", and e5833df allowed only that type and a transparent wrapper, so 0.1.4's header-first tasks broke its contract.

### Security

**`derive_arc_unsafe_wakeable!` would call an `unsafe fn` for you.** The macro called your wake method inside the bodies of the `unsafe fn wake` and `unsafe fn wake_by_ref` it generated. The body of an `unsafe fn` is an unsafe context, so if the name you passed was an `unsafe fn` method, it ran without anyone writing `unsafe`. That covers your own `unsafe fn on_wake`, and anything reachable from `Arc<T>` through `Deref`, like `Option::unwrap_unchecked`. Now the method is called from a plain nested `fn call(arc: Arc<$t>)`, so naming an `unsafe fn` is a compile error (E0133). `wake_by_ref` now goes through `wake(clone_ptr(ptr))`, so it hits the same check. A safe method works the same as before.

### Fixed

**A waker and its own clone could fail `will_wake` in release builds.** std's `Waker::will_wake` compares the data pointer and the vtable's address. Since 0.2.0, `waker_from_arc`, `raw_waker_from_ptr` and every clone took the vtable as `&RawWakerVTableOf::<T>::VTABLE`, a reference to an associated const. A const doesn't have one address, and an optimized build can hold two copies of it. So in release, `clone.will_wake(&waker)` came back `false`. No UB and no lost wake, since `will_wake` is best-effort. But anything that keeps a waker and swaps it only when `!will_wake` ends up re-cloning on every poll, and std's own `Waker::clone_from` does exactly that. Now `UnsafeWakeable` has a provided method, `raw_waker_vtable()`. `derive_arc_unsafe_wakeable!` overrides it with one `static` per type, and both places that build a `RawWaker` take the vtable from it: `raw_clone`, and `raw_waker_from_ptr`, which `waker_from_arc` goes through. A hand-written impl keeps the default, which is the old const, so for those `will_wake` stays best-effort. The trait docs and the README say so.

### Security

**A hand-built `UnsafeWakeableVTable` could lie about its type.** 0.2.0 gave the task vtable a `type_id` so `RegisteredTask::new` could refuse a key registered for another type. But every field was `pub`, so safe code could build a vtable with one type's functions and another type's `type_id`:

```rust
static LIAR: UnsafeWakeableVTable = UnsafeWakeableVTable {
    type_id: small_type_id, // fn() -> TypeId { TypeId::of::<Small>() }
    type_name: small_name,
    ..UnsafeWakeableVTable::of::<Big>()
};
```

Register `LIAR` under a key, and `RegisteredTask::new(Box::new(Small(0)), key)` passes the check. The next `poll` runs `Big`'s `poll` on a `Small`. The task types need their `unsafe impl`, but the only `unsafe` call is `task.poll()`, and its `# Safety` section only asks for the task's own `poll` contract. `Small`'s `poll` has nothing to ask. So the hole was in the crate, not in the caller. Now the fields are private, and the only ways to build one are `UnsafeWakeableVTable::of::<T>()` and `derive_unsafe_wakeable_vtable!`. `type_name()` reads the name.

### Changed

What breaks when you move up from 0.1.4:

- `waker_from_arc(arc)` and `raw_waker_from_ptr(ptr)` take no vtable. `declare_raw_waker_vtable!` still builds, for 0.1 code.
- `RegisteredTask`'s fields are private. Use `key()` and `ptr()`. With `new` the only way to make one, a `RegisteredTask` can only hold a `Box` it made: 0.1.4's `RegisteredTask { key, ptr }` over a slot of an array ([proofs/task-literal-0.1.4](proofs/task-literal-0.1.4/), `slab_slot` prints `slab[1] = 11`) doesn't build on 0.3.1 ([proofs/task-literal-0.3.1](proofs/task-literal-0.3.1/)). 0.4.0's `unsafe fn RegisteredTask::from_raw_parts` brings that back.
